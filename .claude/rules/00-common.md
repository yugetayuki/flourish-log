## 応答

- 常に日本語で回答する。
- 事実と推測を分ける。未確認のことを確定情報として書かない。「確認できていない」と明示する方が信頼される。
- 否定の断定（「〜は存在しない」）を避け、「確認した範囲では見つからなかった」と書く。
- 変更提案は「なぜ（機序）」と「どうする（実装）」をセットで出す。

## 実行環境を前提にしない

同じリポジトリをローカル（Windows）からもクラウド環境からも開く。OS 固有のコマンドやパスを前提にせず、
使えるかどうかを確認してから使う。ローカルにしかないツールに依存する手順は、その旨を書き添える。

## セキュリティ

- シークレットをコードに書かない。API キー・パスワードは環境変数から取る（Node は `process.env.KEY`、
  Python は `os.environ.get("KEY")`）。デフォルト値に実値を入れない。
- SQL は必ずプレースホルダ。`execute("... WHERE id = ?", (val,))` の形式のみ。
  f-string や文字列結合で SQL を組み立てない。
- 入力バリデーションはサービス境界（HTTP ルートの先頭）でのみ行う。内部関数では行わない。
- `subprocess` / `child_process` に外部入力を渡さない。`shell: true` はコマンドが確定している場合のみ。
- 外部サービスへ送ることは公開と同義。キャッシュや索引に残り、後から消しても取り返せない。

## テスト

- 新規関数・HTTP ルート・バグ修正には対応するテストを書く。
- テスト不要: 誤字修正 / コメント変更 / 振る舞いを変えないスタイル調整 / 設定値の単純な変更。
- 外部サービス（LLM API・DB・OS コマンド・ネットワーク）はモックする。
- 完了基準とテストランナーは各プロジェクトの `CLAUDE.md` に従う。

## コード品質

- コメントは WHY のみ。コードを読めば分かる WHAT は書かない。
- YAGNI。「将来使うかも」の抽象化・汎用化はしない。現在の要件だけ実装する。
- 例外を握りつぶさない。`except Exception: pass` や空の `catch {}` は禁止。ログ出力か再スローを必ず伴う。
- HTTP ルートを持つプロジェクトでは、ルートの例外は `{"error": <メッセージ>}` とステータス 500 で返す。
- 周囲のコードと同じ書き方に揃える（コメント密度・命名・イディオム）。

## Git・コミット

- メッセージ形式: `<動詞>: <変更内容>`（日本語可）。動詞は `feat` / `fix` / `docs` / `refactor` / `test` / `chore`。
- コミット禁止。`.gitignore` に無ければ追加してからコミットする:
  - シークレット: `.env` / `*.key` / `credentials.json`
  - DB・生成物: `*.db` / `data/` / `output/` / `dist/` / `build/`
  - キャッシュ: `node_modules/` / `__pycache__/` / `.pytest_cache/` / `.vercel/`
  - OS: `.DS_Store` / `Thumbs.db`
  - 巨大な動画素材: `videos/` 配下の `.mp4` / `.mov`（プロジェクトが明示的に対象としない限り）
- パッケージを追加する前に、標準ライブラリや既存の依存で代替できないか確認する。

## 実行前に確認を取ること

- `git push` / `git commit` / パッケージの追加・削除 / `rm` / デプロイ（`vercel --prod` など）
- 新しい DB・`localStorage` スキーマの追加や変更
- 既存 API・データ形式の後方互換を壊す変更
- 複数ファイルにまたがるリファクタリング
- 課金が発生する外部 API を呼ぶ新機能

確認不要（そのまま進めてよい）:

- 1ファイル・概ね30行以内で、既にテストがあるバグ修正
- テスト追加・コメント修正
- 既存パターンに沿った同一ファイル内の関数・ルート追加
- 読み取り専用の調査・検索
