# 共通開発規約

**このファイルは claude-project-template を正本とする複製で、全複製先で完全に同一。
変更するときはテンプレートを先に直し、そこから各リポジトリへ配る。1つだけ直さないこと。
複製先の一覧と同期手順は正本リポジトリの `README.md`（「00-common.md の同期」）にある。
ここに一覧を書き写さない——複製先が増えたときに、この行だけが古いまま残るため。**

出所は `~/.claude/CLAUDE.md`。あちらは User スコープで1台のマシンにしか存在せず、
モバイルやクラウドのセッションには届かない。同じ挙動をどこでも得るために各リポジトリへ複製している。

## 応答

- 常に日本語で回答する。
- 事実と推測を分ける。未確認のことを確定情報として書かない。「確認できていない」と明示する方が信頼される。
- 否定の断定（「〜は存在しない」）を避け、「確認した範囲では見つからなかった」と書く。
- 変更提案は「なぜ（機序）」と「どうする（実装）」をセットで出す。

## 実行環境を前提にしない

同じリポジトリをローカル（Windows）からもクラウド環境からも開く。OS 固有のコマンドやパスを前提にせず、
使えるかどうかを確認してから使う。ローカルにしかないツールに依存する手順は、その旨を書き添える。

## 進め方

- **同じ事実を2箇所に書かない。** 一覧・件数・設定値・文言はコードの1箇所を「真実」と定め、
  他はそこから導出する。導出できない場所（メタタグ・パッケージの版・ドキュメント）は、
  一致を検査するテストを置くか、値を書かずに真実の場所を参照する。
  導出も検査も参照も無い書き写しは腐る。
- 1つのコミットは1つの意図に対応させる。無関係な整形・リネーム・別件の修正を混ぜない。
  その変更に伴う記録（積み残し・CHANGELOG・版表記）の更新は同じコミットに含めてよい。
- 頼まれた範囲を勝手に広げない。できなかったこと・確認していないことは、黙って落とさずに報告する。
  テストを skip する、対象を絞る、アサーションを消すなど、緑に見せるための操作をしない。
- 解釈が割れて成果物が変わるなら、実装前に聞く。割れても大差ないなら、選んだ前提をコメントか
  決定記録に書いて進める。どの操作に確認が要るかは「実行前に確認を取ること」の一覧に従う。

## セキュリティ

- シークレットをコードに書かない。API キー・パスワードは環境変数から取る（Node は `process.env.KEY`、
  Python は `os.environ.get("KEY")`）。デフォルト値に実値を入れない。
- SQL は必ずプレースホルダ。`execute("... WHERE id = ?", (val,))` の形式のみ。
  f-string や文字列結合で SQL を組み立てない。
- 入力バリデーションはサービス境界（HTTP ルートの先頭）でのみ行う。内部関数では行わない。
- `subprocess` / `child_process` に外部入力を渡さない。`shell: true` はコマンドが確定している場合のみ。
- 外部サービスへ送ることは公開と同義。キャッシュや索引に残り、後から消しても取り返せない。

## テスト

- 新規関数・HTTP ルート・バグ修正には対応するテストを書く。
- テスト不要: 誤字修正 / コメント変更 / 振る舞いを変えないスタイル調整 / 設定値の単純な変更。
- 外部サービス（LLM API・DB・OS コマンド・ネットワーク）はモックする。実物を叩かない。
- ただし**モックを厚く重ねないと書けないテストは、設計が混ざっているサイン**。
  判断・計算はモック不要な関数に切り出し、そこを直接テストする。モックするのは境界であって、ロジックではない。
- 完了基準とテストランナーは各プロジェクトの `CLAUDE.md` に従う。決まっていないプロジェクトは、
  何で緑にするかを先に `CLAUDE.md` へ書く。系統が複数あるなら、
  変更が触れた系統をすべて通す。片方だけ緑にして報告しない。
- **ビルドが通ったことを完了の根拠にしない。** 多くのビルドツールはアプリ本体しか検査せず、
  テストコードの型エラーを素通りさせる。型検査は専用コマンドで明示的に塞ぐ。
- テストを消す・スキップする・期待値を実測値に合わせる、で通すのは修正ではない。
  期待値のほうが誤りだと判断したなら、なぜそう言えるかを説明してから直す。
- Flaky なら、隠さず flaky だと報告する。
- 反復開発でいちばん怖いのは壊れることではなく**黙って劣化すること**。
  要素が一覧から消える・登録したのに結線されていない・設定に実在しない ID が書かれる、
  といった気づけない後退には、専用のガードテストを置く。
  新しい要素を足したら自動で検査対象に入る書き方にする。手で足す検査は必ず忘れる。

## コード品質

- コメントは WHY のみ。コードを読めば分かる WHAT は書かない。
- YAGNI。「将来使うかも」の抽象化・汎用化はしない。現在の要件だけ実装する。
- 例外を握りつぶさない。`except Exception: pass` や空の `catch {}` は禁止。ログ出力か再スローを必ず伴う。
- HTTP ルートを持つプロジェクトでは、ルートの例外は `{"error": <メッセージ>}` とステータス 500 で返す。
- 周囲のコードと同じ書き方に揃える（コメント密度・命名・イディオム）。

## ドキュメント

- **コードから導出できる数字を書き写さない。**「全15本」「テスト25件」は書いた瞬間から腐り、
  腐ったことに誰も気づかない。「真実は `<ファイル>` にある」と参照させる。
  どうしても書くなら、ズレたら機械的に落ちる仕組みを付けるか、「2026-07 時点」と日付を明示する。
- 雛形として生成された README をそのまま残さない。リポジトリを開いた人が最初に見る場所に
  説明が無いのは事故。何をするものか / 動かし方 / 主要コマンド / 構成 / 他ドキュメントへの索引を書く。
- 手順は1箇所にだけ書き、他からはリンクする。多段階の手順やたまにしか使わない作業は
  `.claude/skills/` に置く（必要になったときだけ読み込まれ、常時のコンテキストを消費しない）。
- 機能を足したらその場で関連ドキュメントを直す。「あとで」は来ない。
- コードとドキュメントが食い違っていたら、コードが正。ドキュメントを直す。

## Git・コミット

- メッセージ形式: `<動詞>: <変更内容>`（日本語可）。動詞は `feat` / `fix` / `docs` / `refactor` / `test` / `chore`。
  何を変えたかではなく、何が良くなったかを書く。理由が非自明なら本文に「なぜ」を数行残す。
- デフォルトブランチで作業しない。先にブランチを切る。
- コミット禁止。`.gitignore` に無ければ追加してからコミットする:
  - シークレット: `.env` / `*.key` / `credentials.json`
  - 個人設定: `.claude/settings.local.json` / `CLAUDE.local.md`
  - DB・生成物: `*.db` / `data/` / `output/` / `dist/` / `build/`
  - キャッシュ: `node_modules/` / `__pycache__/` / `.pytest_cache/` / `.vercel/`
  - OS: `.DS_Store` / `Thumbs.db`
  - 巨大な動画素材: `videos/` 配下の `.mp4` / `.mov`（プロジェクトが明示的に対象としない限り）
- パッケージを追加する前に、標準ライブラリや既存の依存で代替できないか確認する。

## 実行前に確認を取ること

- `git push` / `git commit` / パッケージの追加・削除 / `rm` / デプロイ（`vercel --prod` など）
- プルリクエストの作成
- 新しい DB・`localStorage` スキーマの追加や変更
- 既存 API・データ形式の後方互換を壊す変更
- 複数ファイルにまたがるリファクタリング
- 課金が発生する外部 API を呼ぶ新機能

このうち後半4項目（スキーマ・後方互換・複数ファイル・課金 API）は、
気づいた時点で**プランモードに入る**（`EnterPlanMode`）。会話で「これでいいですか」と聞くのではなく、
計画を出して承認を得る。ユーザーが `Shift+Tab` で入っていなくても、こちらから入ってよい。
口頭確認は「確認したつもりで書き始めていた」が起きるが、プランモードは承認まで書き込み自体が発生しない。
プランモードを持たない実行環境では、従来どおり口頭で確認を取る。

確認不要（そのまま進めてよい）:

- 1ファイル・概ね30行以内で、既にテストがあるバグ修正
- テスト追加・コメント修正
- 既存パターンに沿った同一ファイル内の関数・ルート追加
- 読み取り専用の調査・検索
